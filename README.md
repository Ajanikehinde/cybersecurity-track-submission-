Each task folder has its own README with full detail; this top-level file summarizes what was done, why, and how the four tasks relate to each other as a coherent (if small-scale) assessment of a single test host.

Ethics & Scope Note

All scanning, exploitation, traffic capture, and firewall changes in this submission were performed exclusively against a local virtual machine under my own control (10.0.2.15, a VirtualBox NAT-network host) or generated by my own outbound requests to a purpose-built public test endpoint (neverssl.com, designed for exactly this kind of unencrypted-HTTP demonstration). No scanning or traffic interception was performed against third-party production systems, public Wi-Fi, or any network without explicit authorization, in line with the ethics notes on Tasks 1, 3, and 8.

Task 1 — Basic Network Scanning with Nmap

Objective: Identify open ports and running services on a local VM using Nmap, and assess the security implications of what's exposed.

Target: 10.0.2.15 (local VM) Date: 2026-07-07

Scan type	Command	Result
Basic scan	nmap 10.0.2.15	80/tcp open http
Service version scan	nmap -sV 10.0.2.15	80/tcp open http Apache httpd 2.4.68 (Debian)
OS detection	sudo nmap -O 10.0.2.15	Likely Linux; confidence reduced due to limited open ports

Finding: Port 80 (HTTP) was the only open port discovered. HTTP serves web content without encryption, meaning any data — including credentials or session cookies — passed to the service could be read in transit by anyone positioned to observe the traffic. This was later corroborated directly at the packet level in Task 8, where the same kind of HTTP request was captured in cleartext.

Recommendation documented: migrate to HTTPS (port 443) with TLS, keep Apache patched, and close/firewall any port not explicitly required — the last of which is exactly what Task 2 implements against this same host.

Full detail, screenshots, and the Nmap install/ethics writeup: Task1-Nmap/README.md

Task 2 — Basic Firewall Configuration with UFW

Objective: Configure UFW rules on the same test host to control inbound traffic, and verify the rules actually take effect.

Setup: Apache2 was installed and running to provide a real HTTP service on port 80 — the same port identified as open (and unencrypted) in Task 1 — giving the firewall rule something concrete to act on.

Rule applied:

bash
sudo ufw deny 80/tcp

Verification method:

sudo ufw status verbose — confirms 80/tcp is listed as DENY for inbound connections.
sudo systemctl status apache2 — confirms Apache itself is still running and healthy (the firewall change didn't stop the service; it stopped inbound access to the service).
curl http://localhost — returned the Apache default page. This is expected, not a failure: UFW filters inbound traffic arriving over the network interface, not loopback (127.0.0.1) traffic, so a local curl request bypasses the rule entirely. This distinction is called out explicitly in the task README as the correct way to interpret that result — the absence of a change in local behavior is exactly what confirms the rule is scoped correctly.

Why this matters together with Task 1: Task 1 flagged port 80 as an exposed, unencrypted attack surface. Task 2 doesn't fix the encryption problem (that requires HTTPS/TLS), but it demonstrates the access-control half of a real mitigation — restricting who can reach the vulnerable service in the first place, which is one of the standard compensating controls when immediate remediation (e.g., migrating to HTTPS) isn't instantly possible.

Full detail, additional rules, ufw_configuration.sh, and screenshots: Task2-UFW/README.md

Task 7 — Vulnerability Scanning with Nikto

Objective: Run Nikto against the local web server to identify web-specific vulnerabilities and misconfigurations that Nmap's port-level scan wouldn't surface, then categorize and remediate each finding.

Target: The same local Apache instance from Tasks 1 and 2 (10.0.2.15), used here specifically because it's a controlled, intentionally-unhardened server rather than production infrastructure.

Why this task follows naturally from Tasks 1–2: Nmap tells you a port is open and what's listening on it; Nikto goes a level deeper and asks what's wrong with the web application/server behind that port — missing security headers, outdated server banners, default files, directory listing exposure, and similar issues that a simple port scan can't detect.

Deliverables: nikto_scan_results.txt (raw scan output), a findings table categorized by severity (High/Medium/Low/Informational) with a remediation note for each, and an explanation in the task README of what makes Nikto a "noisy" scanner — it flags anything that's potentially a problem rather than confirming exploitability, so findings need manual triage rather than blind trust, unlike a targeted exploit attempt.

Full findings table, severity breakdown, and screenshots: Task7-Nikto/README.md

Task 8 — Capture Network Traffic with Wireshark

Objective: Capture live traffic on the test VM's interface, isolate it by protocol, and use it to directly demonstrate the risk that Tasks 1 and 2 only described in the abstract — that unencrypted HTTP traffic is readable by anyone observing the wire.

Capture interface: eth0 on 10.0.2.15

Traffic generated for the capture:

ICMP echo requests/replies and one DNS query/response for google.com (baseline traffic)
A deliberate HTTP request to neverssl.com (34.223.124.45:80) via curl, chosen specifically because it never redirects to HTTPS, guaranteeing a genuine plaintext capture

Key packets captured and analyzed (TCP conversation, port 52900 → 80):

Packet	Info
1298	[SYN] Seq=0 — client opens connection
1299	[SYN, ACK] Seq=0 Ack=1 — server acknowledges
1300	[ACK] Seq=1 Ack=1 — handshake complete
1301	GET / HTTP/1.1, Host: neverssl.com, User-Agent: curl/8.20.0 — plaintext request
1303–1304	Response segmented across two 1440-byte TCP PDUs (exceeds MSS, reassembled by Wireshark)
1307	HTTP/1.1 200 OK — reassembled response; server header confirms Apache/2.4.6
1308–1312	[FIN, ACK] / [ACK] teardown sequence — graceful connection close

Unencrypted data finding: Packet 1301 shows the complete HTTP request — method, path, host, and client identity — in plain text with no obfuscation, visible in both the protocol tree and the raw hex/ASCII pane. This is the same category of exposure flagged as a risk in Task 1's port-80 analysis, now demonstrated as an observed fact at the packet level rather than a theoretical one.

Also observed: one IPv6 SYN (packet 1296) that received an immediate [RST, ACK] from the destination before the client fell back to a successful IPv4 connection (packet 1298 onward) — noted in the task README as an example of real-world dual-stack fallback behavior.

Why HTTPS prevents this: TLS encrypts the payload of every packet in the session, so an observer positioned on the same network — exactly the vantage point used in this capture — would see only ciphertext and the destination's IP/SNI, not the request line, headers, or response body.

Full glossary, filtered-view screenshots (http, dns, tcp), and the exported wireshark_capture.pcap: Task8-Wireshark/README.md

How the Four Tasks Connect

Rather than four unrelated exercises, this submission was deliberately built as a small end-to-end narrative against one consistent test host:

Task 1 (Nmap) discovers that port 80/HTTP is open and flags it as a theoretical risk because HTTP is unencrypted.
Task 2 (UFW) demonstrates the access-control mitigation — restricting who can reach that exposed port — and correctly interprets why a loopback test doesn't reflect the firewall's actual (network-facing) scope.
Task 7 (Nikto) goes past the port-level view to interrogate the web service itself for application-layer misconfigurations Nmap can't see.
Task 8 (Wireshark) closes the loop by capturing an actual HTTP exchange and showing, at the byte level, exactly the exposure Task 1 predicted — proving the risk empirically rather than asserting it.

This progression — recon → mitigation → deeper scanning → empirical verification — mirrors the real order of operations in a basic security assessment, which is the throughline referenced in each individual task README.
